## Engineering gates
- Gate 0 baseline docs (ARCHITECTURE.md, SECURITY.md, DATABASE.md, MODULE_MAP.md, LOVABLE_RULES.md) are the canonical reference; no DB provisioning or migrations without explicit gate approval — the real Supabase project is not yet initialized.

- NoteBank UI (src/lib/notebank, src/routes/notebank.*) calls only the db-v2 contract (RLS tables + submit_note_version/publish_note_version, direct note_reviews insert); client permission checks via has_permission are UX only — the database is authoritative.
- Question Bank UI (src/lib/questionbank, src/routes/questionbank.*) calls only the Rev6 contract (RLS tables, question_current view, submit/publish/unpublish RPCs, direct question_reviews insert) and must embed questions from question_versions via the explicit FK question_versions_question_id_organisation_id_fkey — two FKs link the tables, so unnamed embeds fail with PGRST201.
- Tenant context: one AuthProvider (src/lib/auth) owns session + active organisation and is the only code that sets `x-organisation-id` on the shared Supabase client; protected modules sit under client-only layout routes (TenantGate). Why: Rev6 `current_org_id()` needs the header, and it must never be built per page — the database re-validates it, so it is context, not authorization.
- CBT Exam Administration (src/lib/cbt, src/components/cbt, src/routes/cbt.*) calls only the Rev6 contract: RLS inserts/updates on exams, exam_questions, exam_eligibility with organisation_id read from current_org_id(), plus publish_exam/close_exam for status. It never sends status, total_marks or created_by and never touches attempts, responses, results or answer keys. The DB stamps created_by and scopes every exam mutation via can_manage_exam (owner, or result.read_all org-wide). Why: the DB column grants, triggers, RLS and lifecycle RPCs are the authority, and scoring stays server-side.
- CBT Student Taking (src/lib/cbt/student.ts, src/components/cbt/student.tsx, src/routes/cbt.my.tsx, src/routes/cbt.take.$attemptId.tsx) uses only the Rev6 candidate RPCs (available_exams, start_attempt, get_attempt_paper, save_response, submit_attempt, results_for_student) and never table access. The countdown is display-only and anchored to server_now, and unsent answers are backed up locally and retried. Why: the database owns the deadline, layout, validation and scoring, and admin CBT files must never import this layer.
- CBT Results & Release (src/lib/cbt/results.ts, src/routes/cbt.results.*, src/routes/cbt.review.$examId.tsx) reads results only through RLS, releases only via release_results(p_exam_id, p_force), and shows answer review only from my_attempt_review. It never writes results/attempts/responses and never computes scores. Why: the database owns permissions (result.read_all/read_class/release), release state, ranking and the released+allow_review gate.
- CBT Manual Marking (src/lib/cbt/marking.ts, src/routes/cbt.mark.$attemptId.tsx) reads responses only through RLS and writes marks only via mark_response(p_response_id, p_marks, p_feedback). It never selects answer keys, never writes responses/results, and never computes totals. Why: the database checks result.mark, student scope, attempt state and mark range, then re-scores the attempt server-side.

- AI governance extends the Rev6 ai_jobs pipeline (enqueue/claim/complete/fail) and ai_prompt_templates; credits go in one append-only ledger keyed to ai_jobs. Why: avoids a parallel AI system and keeps provider calls server-side with draft-only outputs.
- Gate 10 AI governance design (docs/gate10-ai-governance-schema-proposal.md) is the approved spec for future AI migrations; credit reservations live only as ledger rows, never as ai_jobs columns. Why: one source of truth prevents double-reserve/charge.
- Student Management (src/lib/students, src/components/students, src/routes/students.*) uses only the Rev6 tables students, parents, student_parents, enrolments, classes, academic_sessions and the class_roster view through RLS; updates never send organisation_id or user_id, and class changes close the old active enrolment as transferred before inserting. Why: RLS (student.manage, parent.manage, class.manage, student.read) and composite org FKs are the authority, so no migration or SECURITY DEFINER bypass is needed.
- Guardian add/primary/unlink and class assign/withdraw use single invoker RPCs with shared per-student transaction locks; unapplied SQL candidates live in docs/migration-candidates outside tool-managed migrations. Why: atomic writes preserve RLS, and source preparation must not execute a migration; API rollout requires the approved RPCs to exist.
- Curriculum Bank (src/lib/curriculum, src/routes/curriculum.*) is read-only over existing curricula/curriculum_versions/curriculum_units/curriculum_topics via RLS, never sends organisation_id and defaults to the published version. Why: tenant scope and publication state are owned by the database; writes await approved curriculum gates.
- Finance Phase 1 uses isolated mock fixtures and a pure deny-by-default capability helper, with no Finance network calls; the demo overview remains behind the unchanged TenantGate. Why: synthetic figures are not financial access, and live permission integration requires a later approved phase.
- Finance Phase 2 (src/lib/finance/live.ts, src/components/finance/live.tsx, src/routes/finance.{catalogue,invoices.*,payments,refunds,accounts,my}.tsx) reads only through RLS and writes money only through migration 006 functions (create_invoice, issue_invoice, void_invoice, write_off_balance, apply_wallet_to_invoice, record_manual_payment, request/approve/reject/complete_refund). Direct writes are limited to the price list and deleting DRAFT invoices; it never sends unit_price, never writes the ledger, and never calls initiate_payment/attach_checkout. The Phase 1 /finance overview stays demo-only. Why: the ledger, numbering, scholarships and separation of duties live in the database; online checkout needs a server secret + webhook gate.
- Learning Progress / CAS (src/lib/cas, src/components/cas, src/routes/learning.*) reads mastery only via learning_dashboard() and security_invoker views, and writes only via migration 007 functions. It never computes mastery and edits only teacher_comment when approving a parent report. Families only tick off reading/practice tasks (mark_intervention_done). Why: released-only visibility and staff scope (staff_can_view_results) are enforced in the database.
- AI drafting (src/lib/ai, src/components/ai, src/routes/ai.*) only enqueues through request_ai_* with a fresh idempotency key per press, and only cancels/approves/reviews via cancel_ai_job, approve_ai_job, review_ai_diagnostic, review_ai_diagnosis_narrative. It never calls a provider, a worker function, prompt tables or a publish RPC. Why: governance (plan, limits, credits, approval, kill switch) is in the database and outputs must stay drafts for the existing review workflow; the worker is a separate server gate.
- Onboarding (src/lib/onboarding, src/routes/welcome.tsx, src/routes/members.*) uses only create_organisation, invite_member and accept_invitation. /welcome is deliberately outside TenantGate. After joining/creating it writes the org preference and reloads; it never touches AuthProvider, sessions or the org header. Why: auth/session is a protected area; the invitation token is shown once and only its hash is stored.
